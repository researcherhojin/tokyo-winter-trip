# 이 프로젝트의 개발·검증 절차

현재 작업 범위·중단 상태·후속 우선순위는 [PROJECT_STATUS.md](PROJECT_STATUS.md), 사진별 현재 수치는 [PHOTO_ARCHIVE.md](PHOTO_ARCHIVE.md)를 기준으로 합니다. 아래 절차는 재개 시 적용하며 백그라운드 작업을 자동 시작하지 않습니다.

OpenAI의 [Codex Best practices](https://learn.chatgpt.com/docs/learn/best-practices)에서 맥락 제공, 짧은 AGENTS.md, 복잡한 작업의 사전 설계, 테스트와 리뷰, 반복 작업 자동화를 확인했습니다. [공식 코드 리뷰 규칙 안내](https://developers.openai.com/blog/custom-code-review-rules-for-codex)는 프로젝트의 중요한 불변 조건을 좁고 구체적으로 기록하는 방식을 설명합니다. 아래 4단계는 이를 이 여행 앱에 맞춘 **프로젝트 운영 방식**이며 공식적으로 지정된 모델 조합은 아닙니다.

| 단계 | 이 앱에서 할 일 | 완료 근거 |
| --- | --- | --- |
| 요구·근거 | 사용자 문제 재현, 원본 일정과 공식 자료 확인 | 확인된 사실·예정·미확인 구분 |
| 설계 | UI 레퍼런스·사용 흐름·변경 모듈·성공 조건 결정 | 디자인은 DESIGN_REFERENCES, 구조는 ARCHITECTURE에 기록 |
| 구현 | 기존 코드와 도구로 필요한 기능 구현 | 실행 가능한 코드, 가역적 로컬 변경 |
| 검증·리뷰 | 자동 검사, 실제 브라우저, 반례 재현, 캡처 비교 | 명령 결과·실측 값·검증 한계 |

모든 작업을 여러 모델에 순서대로 넘기지 않습니다. 기본은 한 작업 흐름으로 진행하고, 독립 리뷰가 필요한 복잡한 인증·과금·배포·데이터 변경은 별도 리뷰 범위를 정합니다. 별도 외부 모델의 독립 리뷰나 gstack 실행기를 돌린 것은 아닙니다.

## 2026-10-18 · 공식 지침을 적용한 병렬 개선

OpenAI Docs 스킬로 [Codex Best practices](https://learn.chatgpt.com/guides/best-practices), [Subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents), [Iterating Development Workflows with Codex](https://developers.openai.com/cookbook/examples/codex/iterating-development-workflows-with-codex)를 직접 확인했습니다. 짧은 저장소 지침, 관찰 가능한 완료 기준, 독립 작업의 위임, 변경 충돌 관리와 결과 검증을 이 저장소에 맞춰 적용합니다. 아래는 프로젝트가 선택한 실행 방식이며 공식 문서의 예제 전체를 의무 절차로 채택한 것은 아닙니다.

사용자의 명시적 요청으로 API·디자인·여행 정보 담당을 병렬 실행합니다. API 담당은 서버·공유 계약·조회 훅, 디자인 담당은 화면·CSS, 정보 담당은 데이터·출처 문서만 수정합니다. 주 에이전트는 계약 연결, 브라우저 검증과 Notion 결과 기록을 책임집니다. 같은 파일을 동시에 수정하지 않고 필요한 계약 변경은 구현 전에 전달합니다.

| 개선 범위 | 관찰 가능한 완료 기준 | 검증 |
| --- | --- | --- |
| 화면별 조회 API | 여행·테마·준비 항목을 각각 JSON으로 조회. 로컬에서도 동작. UI가 실제 소비 | 실제 HTTP 응답·공통 응답 계약·실패 및 미지원 메서드 검사 |
| 통신 실패 | 키 없음·네트워크 오류·잘못된 JSON에도 기본 일정·테마·준비 체크 사용 | 응답 차단·잘못된 응답 재현 |
| 디자인 일관성 | 세 화면의 글자·색·콘텐츠 폭·버튼·상태 표현을 공통 규칙으로 구성 | PC·모바일 캡처와 실제 탐색·검색·체크·상세 열기 |
| 장소 설명 | 체험·방문 순서·접근·현장 주의·공식 출처를 상세에서 확인 | 공식 자료 대조·상세 렌더링 확인. 미래 운영과 예약은 별도 표시 |
| 저장 범위 | 개인 체크·저장은 기기 로컬에 유지. API는 여행 안내만 제공 | 저장 후 이동·새로고침 유지, API에 체크 상태 미포함 |

세 화면용 API 분리는 공유 편집·인증·데이터베이스를 도입한다는 뜻이 아닙니다. 신규 유료 API 활성화나 배포는 이번 로컬 개선에 포함하지 않습니다. 결과와 남은 한계는 검증 후 `docs/VERIFICATION.md`와 같은 Notion 개발 기록에 갱신합니다.

## 완료 명령

```bash
npm run check
npm run dev
npm run qa:browser
```

`check`는 빌드·TypeScript·동작·철자·키 패턴을 검증합니다. 브라우저 검증은 실행 중인 서버에서 지도 연결, 날짜별 마커, 사진 디코딩, 화면 폭, 터치 영역, 대비, 모달·지도 오류 복구를 확인하고 JSON과 캡처를 남깁니다. 기본 대상은 로컬 서버이며 외부 배포를 생성하지 않습니다. 키가 없다면 그 상태를 기록하고 실제 지도 연결 성공으로 표시하지 않습니다.

Playwright CLI 기본 경로는 `~/.codex/skills/playwright/scripts/playwright_cli.sh`입니다. 다른 설치 위치는 `PLAYWRIGHT_CLI`로 지정합니다. 브라우저·로컬 네트워크 권한이 막히면 권한 제한을 구체적으로 보고하고 호스트의 정식 승인 절차를 사용합니다.

## 반례 중심 리뷰

| 위험 | 정상 동작과 구분하는 반례 |
| --- | --- |
| 지도 라이브러리 오류 | core에만 LatLngBounds가 있는 모의와 실제 SDK 모두 확인 |
| 지도 요청 차단 | SDK 요청을 일부러 차단해도 일정·길찾기 유지, 해제 후 복구 |
| Notion 불완전 응답 | 일차 표 하나 누락·인증 실패면 마지막 정상 일정 유지 |
| 예약 상태 오해 | 합의·결제 기록만으로 확정 배지를 붙이지 않는지 확인 |
| 화면 진단 누락 | hover 대비, 작은 클릭 영역, 스크롤한 모달 닫기, 좁은 화면 확인 |
| 도구 실행 과장 | 모의·라이브·배포 검증을 각각 표기. 외부 리뷰 미실행은 명시 |

수정 전후 사진과 수치만으로 디자인이 좋다고 결론내리지 않습니다. 지도 중심 구조와 모바일 시트로 재설계를 구현했으며, 자동 검사 결과와 사용자의 시각적 선호 평가는 구분합니다.

브라우저 QA는 전용 tokyo-audit 세션에서만 화면 폭을 바꾸고 종료 시 닫습니다. 사용자에게 보여주는 tokyo-design 세션은 viewport:null 설정으로 열며 검사에서 크기를 변경하지 않습니다. 바깥 창이 넓어도 이전 세션의 모바일 뷰포트가 남을 수 있으므로 innerWidth와 outerWidth를 함께 확인합니다.
